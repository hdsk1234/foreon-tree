## Firebase 프로젝트 없이 바로 실행

실제 Firebase 프로젝트와 결제 설정 없이 로컬 플레이를 개발할 수 있다.

```sh
npm ci
npm --prefix functions ci
npm run dev:local
```

이 명령은 함수 빌드 → Auth/Firestore/Functions Emulator 시작 → 85개 동 생성 → 7일짜리 로컬 이벤트 생성 → 매분 순위 집계 → Vite 실행을 자동으로 수행한다. `.env.local`을 만들지 않고 로컬 전용 demo 설정을 Vite 프로세스에 주입한다. 실제 Firebase 프로젝트/자격증명을 생성하거나 수정하지 않는다.

터미널에 출력되는 **로컬 플레이 주소**를 연다. 5174부터 5194 사이의 빈 포트를 찾으며 기존 서버를 종료하지 않는다. `npm run dev`와 `npm run dev:local`은 모두 전체 로컬 환경을 실행한다. 화면만 보는 Vite 서버는 `npm run dev:preview`로 분리했다. 기본 프로젝트 ID는 Emulator 전용 `demo-foreon-tree`다. Auth/Firestore/Functions 포트는 각각 9099/8080/5001을 사용한다. 동일 작업 폴더에서 다시 실행하면 새 Emulator를 띄우지 않고 기존 실행 주소(또는 준비 중 안내)를 출력한다. 다른 프로그램이 해당 포트를 쓰고 있으면 시작 전에 서비스와 포트를 안내하며, 임의로 종료하지 않는다. Emulator 안에서만 시드/로컬 집계가 실행되도록 호스트와 프로젝트를 검사한다.

최초 방문 시 게스트 로그인 후 **이 동으로 참가**가 활성화된다. 동 참가 후 현재 트리를 터치하면 동 누적 경험치·성장 진행률·표시 레벨·우리 동 예상 순위가 즉시 갱신된다. 서버에는 기본 5초 단위로 저장하고 우리 동·관전 동의 확정 점수는 실시간 동기화한다. 전체 순위는 트리와 랭킹 화면에서 동일한 매분 집계 문서 하나로 받는다. 미전송 경험치는 UID/이벤트별 기기 저장소에 보관해 새로고침 후 복구한다. 이 환경은 개발용이며 서버 종료 시 데이터는 초기화된다. Emulator 데이터를 초기화한 경우 인증/Firestore 캐시가 이전 실행과 맞지 않을 수 있다. 초기화한 이벤트 ID를 재사용하지 말고 명시적으로 로그아웃 후 다시 참가한다. 인증 오류만으로 기존 계정을 자동 교체하지 않는다. 실제 프로젝트 생성/Blaze 연결은 배포 단계에서 진행한다.

## 개발 환경

Node.js 22, npm, Emulator가 요구하는 Java 21 이상을 준비한다. 프론트엔드와 함수 의존성은 독립 설치한다.

```sh
npm ci
npm --prefix functions ci
cp .env.example .env.local
```

로컬에서는 .env.local에 VITE_FIREBASE_PROJECT_ID=demo-foreon-tree, VITE_FIREBASE_API_KEY=demo-only, VITE_FIREBASE_AUTH_DOMAIN=localhost, VITE_FIREBASE_APP_ID=demo-only를 설정한다. 이 값들은 Emulator 전용 식별값이며 실제 프로젝트 ID/자격증명이 아니다. VITE_USE_EMULATORS=true를 유지한다. VITE_EVENT_ID에는 로컬에서 만든 이벤트 문서 ID를 넣는다.

```sh
npm run emulators
```

다른 터미널에서 초기 데이터를 생성하고 Vite를 실행한다.

```sh
GCLOUD_PROJECT=demo-foreon-tree FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 npm run seed
npm run dev:preview
```

Emulator UI에서 events/{VITE_EVENT_ID} 문서를 만들고 status=active, startsAt=현재 이전 Timestamp, endsAt=미래 Timestamp를 지정한다. 실제 날짜/이벤트 ID를 하드코딩한 운영 이벤트는 자동 생성하지 않는다. 로컬 Scheduler 자동 실행을 전제로 하지 말고 Emulator UI의 예약 함수 실행 도구 또는 Firebase 문서의 로컬 예약 함수 호출 방법으로 publishRankings를 실행한다. 집계 전에는 초기 0점 트리가 표시된다. 잘못된 프로젝트로 연결하지 않도록 Emulator demo ID를 일치시킨다.

```sh
npm test
npm run build
npm run build:functions
npm run test:rules
npm run test:scoring
npm run test:integration
```

일반 테스트와 Rules Emulator 테스트는 분리한다. 함수 통합·Auth 전체 흐름·실제 브라우저 검증은 ROADMAP을 따른다. 로컬만으로 Google의 실제 OAuth 리디렉션/팝업을 완전히 검증했다고 간주하지 않는다.

## 실제 Firebase 설정과 배포

Firebase Console에서 하나의 실제 프로젝트를 선택하고 Web app, Authentication(Anonymous/Email·Password/Google), Firestore, Functions, Hosting을 구성한다. 실제 Web app 설정을 .env.local에 복사하고 운영 빌드에서는 VITE_USE_EMULATORS=false로 지정한다. .firebaserc의 projects는 의도적으로 비어 있다. `firebase use --add`로 운영자가 확인한 실제 ID를 매핑한다. 비밀키/서비스 계정 JSON은 저장소나 VITE_ 변수에 넣지 않는다. Google 허용 도메인과 이메일 인증/재설정 템플릿을 설정한다.

운영 초기 데이터 생성은 관리형 자격증명 또는 ADC를 구성하고 실제 GCLOUD_PROJECT와 `--production`을 명시해야 한다. 기존 문서는 유지되므로 정정이 필요하면 별도 검토한 마이그레이션을 작성한다.

```sh
npm run build
npm run build:functions
npx firebase deploy --only firestore,functions,hosting --project YOUR_CONFIRMED_PROJECT_ID
```

YOUR_CONFIRMED_PROJECT_ID는 명령 설명용 자리표시자다. 이 명령은 출시 조건을 충족한 뒤 실행한다. Firestore TTL 및 Cloud Scheduler 설정/권한도 배포 후 확인한다. Hosting은 dist와 SPA rewrite를 사용한다.

## 비용과 운영 예산

Cloud Functions 배포에는 결제가 연결된 Blaze 요금제가 필요하다. Functions 실행/CPU·메모리/네트워크, Firestore 읽기·쓰기·저장/TTL, Hosting 전송량, Scheduler, 빌드·Artifact Registry 보관 비용을 함께 고려한다. 무료 할당량 안에서도 빌드/이미지 저장 등 관련 비용이 발생할 수 있다. [Firebase 요금제](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans)와 [공식 가격 계산기](https://firebase.google.com/pricing)를 사용해 배포 리전·무료 할당량·실제 사용량 기준으로 재계산한다.

예상 사용량 예시(가격 확정 견적 아님): 하루 1,000명이 10분씩 참여하고 매 5초 전송하면 120,000배치/일, 약 360,000점수 관련 쓰기/일(배치당 3회)이다. 매분 집계 문서를 구독하면 사용자 순위 읽기는 약 10,000회/일 + 최초 연결/재연결이다. 종일 활성 이벤트 하나의 집계는 동 목록 약 122,400회/일 + 동 원장 최대 122,400회/일 읽기, 결과 1,440회/일 쓰기이며 참가·함수 검증 읽기·본인 점수 구독·트랜잭션 재시도는 별도다. 가격을 R(10만 읽기당), W(10만 쓰기당)라 하면 이 예시의 월 기본 DB 비용은 `30 × (일 읽기/100000 × R + 일 쓰기/100000 × W)`에 저장·전송·TTL 비용을 더해 산정한다.

검증 전 운영 예산은 예시로 월 US$10~50을 검토하되 이는 한도나 청구 예상 보장이 아니다. 위 사용량에 대한 함수/검증 읽기/네트워크까지 공식 계산기에 입력하여 승인된 예산을 정한다. 높은 참여율·재접속·잘못된 클라이언트 호출은 초과 비용을 유발한다. maxInstances=5, minInstances=0, 배치 제한을 사용하되 전체 지출을 보장하는 상한은 아니다. 배포 이미지 정리 정책도 설정한다.

**예산 알림은 사용량이나 지출을 자동으로 차단하지 않는다.** 예산 알림과 실제 사용 중단 기능은 별개다. 알림 수신자를 지정하고 호출 급증 시 이벤트 중단·함수 제한·청구 점검 운영 절차를 마련한다. [공식 예산 알림 문서](https://firebase.google.com/docs/projects/billing/budget-alerts)를 따른다.

## 개인정보와 출시 상태

기본은 게스트다. 정식 계정 전환은 만 14세 이상 또는 법정대리인 동의 등 필요한 요건 확인 전 UI에서 제공하지 않는다. 생년월일/학교/호수 등 추가 식별정보를 임의로 수집하지 않는다. 제공된 단지 데이터(85개 동, 12,032세대)는 기획 초기값으로 실제 정보 확인이 필요하다. 미전송 경험치는 LocalStorage 저널과 IndexedDB 배치 원장으로 보존한다. 브라우저 데이터 직접 삭제·저장소 회수까지 보장하지 않으며 저장 권한이 없으면 입력을 차단하고 안내한다. 현재 단계는 최종 출시 품질 검증을 마친 서비스가 아니다.

### 사용자 제공 트리 디자인 적용 — 2026-11-24

## 2026-11-25 레벨별 입력 보상 및 장기 성장 개편 (최신 기준)

이 절은 기존 고정 기본 EXP 및 기존 성장 비율 유지 설명보다 우선한다. 레벨별 기본 EXP는 Lv.1~10 순서대로 1,000 / 2,000 / 3,000 / 5,000 / 8,000 / 12,000 / 18,000 / 27,000 / 40,000 / 60,000이다. `functions/src/economy.json`의 `levelBaseUnits`와 `levels.json`을 서버/브라우저가 공유한다. 이전 디자인을 선택해도 최고 해금 레벨로 보상한다. 입력 하나로 레벨 경계를 넘으면 다음 입력부터 새 기본 EXP를 적용하며, 같은 배치 안에서도 순차 계산한다. 서버는 Transaction에서 읽은 동 누적 EXP로 계산하고 클라이언트가 제시한 레벨/배율을 신뢰하지 않는다.

10레벨 기준은 누적 25,000,000,000,000 EXP다. 난이도 가정은 동당 500명, 각자 하루 1시간, 초당 3회 입력(주간 37,800,000회)이다. 모든 입력에 최대 콤보·5배 선물을 부여하는 실제보다 유리한 가정에서도 최소 62,642,252회(동일 활동량 약 11.60일)가 필요하다. 실제로는 콤보 준비/감쇠와 선물 대기 때문에 더 오래 걸린다. 이는 가정 기반 하한이며 실제 플레이 예측치는 아니다. `node scripts/balance-economy.mjs`로 재검산한다.

기존 누적 EXP와 승인/미전송 원장은 삭제하지 않는다. 레벨은 새 임계값으로 다시 계산하므로 기존 표시 레벨은 낮아질 수 있다. 승인된 배치는 기존 영수증 그대로 반환하며 재합산하지 않는다. 이전 클라이언트의 입력 시각 없는 배치는 기존 고정 기본 보상으로 처리하는 호환 경로를 유지한다. 신규 입력은 입력 시각을 포함해 레벨별 보상을 적용한다. 다중 사용자 동시 입력/오프라인 전송으로 서버가 더 높은 동 점수를 읽으면 승인 시 서버 계산으로 동기화한다. 랭킹의 레벨도 저장된 과거 actualLevel 대신 누적 EXP로 재계산한다.

트리 디자인 개편: 단계별 크기·팔레트·수정/루비/오로라/왕관/별자리 장식을 구분하고, 트리 화면의 `트리 꾸미기`에서 레벨별 개인 꾸미기를 제공한다. 설정은 이 기기에 계정·이벤트·동별로 저장한다. `/developer`에서는 모두 해금되며, `/tests/fixtures/tree-gallery.html`에서 서버 기록 없이 비교할 수 있다. 디자인 설정은 `src/engine/treeDesign.mjs`, 렌더링은 `ParticleScene.ts`, 해금 목록과 저장 계약은 GAMEPLAY_NOTES.md 최신 절 참조.
